## What was built (WP3.1)

Two new tables plus a nullable extension to the existing `ReviewTask`:

1. **`ApprovalWorkflow`** (`prisma/schema.prisma`) — a named, ordered sequence of stages a workspace can define, `active` boolean to retire one without deleting it. Migration `20260829040000_add_approval_workflows` (hand-written SQL, not `prisma migrate dev` — see "Why hand-written" below).
2. **`ApprovalWorkflowStage`** — one stage per `(workflowId, stageIndex)`, a `name`, and `requireOwner: boolean`. There is no per-stage named-approver list: this app's `WorkspaceRole` is just `"owner" | "member"` (confirmed via research this session — no richer role system exists anywhere), so a stage that needs to be sensitive marks `requireOwner: true` rather than naming specific people. A plain member can decide any stage that doesn't.
3. **`ReviewTask.workflowId`/`currentStageIndex`** — both nullable. `null` means the pre-existing plain single-decision behavior (unchanged — `updateReviewTaskStatus` still works exactly as before for a task with no workflow). Set means the task only reaches `status: "approved"` once `currentStageIndex` has cleared every stage.
4. **`lib/approvals/engine.ts`** — pure decision logic, no Prisma import (same split as `lib/bank-match/matcher.ts` pure-engine vs `models/bank-matches.ts` persistence): `decideStage` (advance/approved/rejected), `canDecideStage` (role gate), `findCurrentStage`. Unit-tested in `lib/approvals/engine.test.ts`.
5. **`models/approval-workflows.ts`** — CRUD: `createApprovalWorkflow`, `listApprovalWorkflows`/`getApprovalWorkflow` (React `cache`), `updateApprovalWorkflow` (name/active only), `replaceApprovalWorkflowStages` (wholesale delete+recreate — see the in-flight-task caveat in its doc-comment), `deleteApprovalWorkflow` (safe: `ReviewTask.workflowId` is `ON DELETE SET NULL`), `startWorkflowOnReviewTask` (attaches a workflow to an already-created task, starting it at stage 0). Not `"use server"` — trusts the workspaceId it's handed, same convention as `models/review-tasks.ts`/`models/bank-matches.ts`. No server actions or UI call these yet (that's WP3.2).
6. **`models/review-tasks.ts`** — `createReviewTask` gained an optional `workflowId` param (starts the task at stage 0, status `"in_review"`, instead of the plain `"open"` default); new `decideReviewTaskStage(workspaceId, taskId, decision, actorId, actorRole)` is the workflow-aware counterpart to `updateReviewTaskStatus` — throws `review_task_has_no_workflow` for a plain task, `stage_requires_owner` if a member tries an owner-gated stage, otherwise advances the stage or resolves the task, writing a `review_task_stage_decided` audit event either way.
7. **Module key** `approval-workflows` (`lib/modules/index.ts`), `tier: "optional"`. Started this session as `activation: "request"`, flipped to `"enable"` once WP3.2 shipped the settings UI (same precedent as `bank-match` going `"request"` → `"enable"` after WP2.2) — still `tier: "optional"`, so each workspace has to turn it on itself under Settings → Modules; it is not on by default even for a finance workspace.
8. **`lib/workspace-scope.ts`** — `ApprovalWorkflow`/`ApprovalWorkflowStage` added to the scoped-models list.

### A real bug this WP's browser verification caught (and fixed)

`components/workspace/review-inbox.tsx`'s detail pane is client state (`detail`), fetched once per `effectiveSelectedId` change via a `useEffect`. `router.refresh()` — what the pre-existing `changeStatus` handler already relied on — only re-renders the *server-rendered* list; it does nothing for that client-fetched `detail` object, since `effectiveSelectedId` doesn't change when a decision resolves the currently-selected task. The plain-status path never surfaced this because it also writes an *optimistic* `optimisticStatus` map the status buttons read from directly. The new workflow buttons had no equivalent optimistic layer, so after clicking "Approve stage" the UI kept showing the stage it was on *before* the click — the write had actually succeeded server-side (confirmed by reloading the page), but nothing on-screen reflected it without a manual refresh. Fixed by adding a `refetchDetail(taskId)` helper that explicitly re-runs `getReviewTaskDetailAction` and calls both `decideStage`/`startWorkflow` handlers before `router.refresh()`. Re-verified live afterward: clicking through both stages of a two-stage workflow, and rejecting a one-stage workflow, both update the pane immediately with no reload.

### Why hand-written migration, not `prisma migrate dev`

Tried it first (real Postgres was up, so it's technically usable here unlike the local PGlite dev DB). It refused non-interactively as expected, but its dry-run warned it would **drop `document_chunks.embedding`, `document_chunks.text_tsv`, and `document_field_values.value_text_norm`** — pgvector/tsvector columns that exist in the live schema via raw SQL migrations but were never (and can't be, cleanly) modeled in `schema.prisma`. This is pre-existing baseline drift, not something this session introduced. Given that, every migration in this repo's recent history is hand-written to mirror the existing `CREATE TABLE`/index/FK/`DROP POLICY IF EXISTS`+`CREATE POLICY` shape exactly (see `20260829030000_add_bank_matches`, `20260829020000_add_accounting_entities`) rather than machine-generated — this migration follows the same practice, and `migrate dev` should keep being avoided against this schema until that drift is deliberately reconciled.

### Browser login is still broken in this session (RESOLVED in a later session — root cause found and fixed)

**Update 2026-08-29 (later session):** root-caused and fixed, verified live. Two compounding middleware bugs: (1) `proxy.ts` built a bare `NextResponse.redirect` for signed-out visitors to protected paths, discarding `updateSession`'s response and with it the idle path's cookie deletions — so the browser kept its stale `docubite-last-seen` cookie forever; (2) `isIdle` (lib/supabase/middleware.ts) compared only that cookie against the 15-minute timeout, so a brand-new sign-in was judged idle on its first protected request and revoked server-side (`signOut()`), bouncing to `/login` — permanently, since (1) meant the stale cookie survived every bounce. This explains all six findings below, including why a hand-minted valid session cookie also bounced. Fixed both (redirects now carry the middleware's set-cookie headers; a session whose `last_sign_in_at` is newer than the last-seen timestamp is never idle), and verified live: a fresh login with a deliberately planted one-hour-stale last-seen cookie now reaches `/workspaces`. The `@react-email/render` gap flagged below was also fixed (installed, render verified). Both on master. The original investigation notes are kept below for the record.

A second, longer session was spent specifically trying to fix this (at the user's request) before being told to drop it and move on. What's now confirmed, in order:

1. **The credentials are valid and Supabase issues a real token for them.** A raw `fetch` to `https://<project>.supabase.co/auth/v1/token?grant_type=password` from the page's own console, with the exact same email/password, returns `200` with a real `access_token` — repeatably, every time.
2. **The account has no MFA factor enrolled** (the token response carries no `factors`/`aal`/`amr`), so `LoginForm`'s post-sign-in `getAuthenticatorAssuranceLevel()` branch can't be sending it somewhere unexpected like `/mfa/challenge`.
3. **The login page is fully hydrated and its real `onSubmit` handler is intact** — confirmed by reading the button's `__reactFiber$`/`__reactProps$` keys directly and finding a genuine `onSubmit` function on the form.
4. **Invoking that real `onSubmit` directly** (bypassing click/keyboard entirely, calling the React prop function with a fake event) **behaves correctly for a bad password**: `preventDefault` fires synchronously, `signInWithPassword` resolves, and the inline `FormError` ("That email and password do not match an account.") renders on screen with no navigation — proving the handler, the Supabase client, and the error-rendering path all work.
5. **The exact same call with the real password does not show a success state, an error, or a `/workspaces` request in the server logs — it just lands back on `/login`.** `performance.getEntriesByType("navigation")[0]` on the resulting page shows `type: "navigate"`, `redirectCount: 0`, and an empty `document.referrer` — i.e. this is not the browser following a client-side `window.location.href = "/workspaces"` into a server-side redirect back to `/login` (that would show `redirectCount >= 1` or a referrer). The dev server's own request log across the entire session **never once shows a `GET /workspaces`** — not even a redirected one.
6. Manually minting a session cookie in the exact format `@supabase/ssr` expects (from the same real token in step 1) and navigating to `/workspaces` **still lands back on `/login`** — so this isn't even specific to the sign-in call; something about this browser tab's relationship with this dev server rejects an authenticated session outright, independent of how it got there.

That last point is the strongest lead: this looks like it sits at the `proxy.ts` middleware / cookie level, not in `LoginForm`, not in Supabase, and not in anything this session's Dext-parity changes touched (nothing here touches auth, cookies, CSP, or middleware). Given the constraint of "keep making forward progress on Phase 3," this was intentionally left unresolved rather than continuing to burn the session on it — whoever picks this up next should start from point 6 above: confirm whether `proxy.ts` is rejecting a validly-cookied request in this specific browser/environment (a cookie attribute mismatch — domain, `Secure` over plain `http://localhost`, `SameSite` — would explain a session being silently ignored server-side without ever showing up as an explicit redirect).

WP3.3/3.4's live verification fell back to model-layer `tsx` scripts against the real Postgres instance for this reason — thorough for the model/engine logic, but not a substitute for actually clicking through the new `/expenses` page or the reminder emails' target URLs in a browser.

## What was built (WP3.3)

Confirmed via research this session that there was **no existing `ExpenseClaim` concept anywhere** — only the unrelated `expense_receipt` **document template** (a single-receipt extraction schema: merchant/purchase_date/total/tax_total/etc, not a claim-level grouping/submitter/status). This is a green-field model.

1. **`ExpenseClaim`** (`prisma/schema.prisma`) — a submitter, optional title, `status` (`draft | submitted | approved | rejected`, the same shape as `ReviewTask.status` with "draft" standing in for "open"), a frozen `total`/`currencyCode` (computed once at submission, never live-recomputed — see its own doc-comment for why), and its own `workflowId`/`currentStageIndex` pair. Migration `20260829050000_add_expense_claims` (hand-written, same reasoning as WP3.1's migration for avoiding `prisma migrate dev` against this schema's pgvector/tsvector drift).
2. **`ExpenseClaimItem`** — a plain join row linking one claim to one `expense_receipt` Document (`@@unique([claimId, documentId])` enforces "not claimed twice" at the DB level, backed up by a friendlier `document_already_claimed` check in the model layer first).
3. **Deliberately does NOT reuse `ReviewTask`.** `ReviewTask.documentId` is a required, non-nullable FK to a single `Document`, and a `Document` is always the product of one uploaded file going through OCR/extraction (`Document.fileId` is required) — there's no way to make a claim's own metadata (submitter, title) itself a `Document` without fighting that invariant everywhere else. Instead `ExpenseClaim` reuses only the lower-level `ApprovalWorkflow`/`ApprovalWorkflowStage` tables and `lib/approvals/engine.ts`'s pure functions directly, via its own `workflowId`/`currentStageIndex` — the exact same shape `ReviewTask` already uses, just independent of it.
4. **`models/expense-claims.ts`** — `createExpenseClaim` (validates every document is an in-workspace `expense_receipt` not already claimed, creates claim + items in one call), `listExpenseClaims`/`getExpenseClaim`/`listUnclaimedExpenseReceiptDocuments` (React `cache`), `deleteExpenseClaim` (draft-only), `submitExpenseClaim` (locks in `total`/`currencyCode` from the linked receipts' own `reviewedData`, optionally starts a workflow at stage 0 exactly like `createReviewTask`'s `workflowId` option), `updateExpenseClaimStatus` (the plain no-workflow approve/reject path, refuses a claim that has a workflow), `decideExpenseClaimStage` (the workflow-aware counterpart, identical shape to `models/review-tasks.ts`'s `decideReviewTaskStage`).
5. **`app/(app)/workspaces/[workspaceId]/expense-claim-actions.ts`** (new) — `"use server"` CRUD + decision actions. Authorization split three ways: create/delete/submit require the actor to be the claim's own submitter *or* a workspace owner (mirrors `canCreateRule`'s "yours, or an owner's call" bar); a plain (no-workflow) decision requires an owner outright; a workflow decision defers entirely to `decideExpenseClaimStage`'s own per-stage `requireOwner` check.
6. **`app/(app)/workspaces/[workspaceId]/(chrome)/expenses/page.tsx`** (new) — lists every claim in the workspace (seeing a claim you might need to approve requires seeing it), a "New claim" form checking off unclaimed receipts (`components/workspace/expense-claim-form.tsx`), and one row per claim (`components/workspace/expense-claim-row.tsx`) with contextual actions: Submit (with an optional workflow picker) + Delete while a draft you own, Approve/Reject once submitted and you're allowed to decide its current position.
7. **Module flip**: `expense-approvals` went from `activation: "request"` to `"enable"` (same precedent as `bank-match` and `approval-workflows` before it), gained a sidebar nav entry ("Expenses", new `receipt` icon key in `components/shell/sidebar.tsx`).
8. **`lib/workspace-scope.ts`** — `ExpenseClaim`/`ExpenseClaimItem` added to the scoped-models list.

## What was built (WP3.4)

1. **`lastReminderAt DateTime?`** added to both `ReviewTask` and `ExpenseClaim` (migration `20260829060000_add_reminder_timestamps`) — null until the first reminder for that item goes out.
2. **`lib/reminders/engine.ts`** — the pure part, same split as `lib/approvals/engine.ts`: `isReminderDue({ pendingSince, lastReminderAt, now })`, gated on two constants: `REMINDER_STALE_HOURS` (48h — how long something sits before its first nudge) and `REMINDER_REPEAT_HOURS` (72h — minimum gap between repeats for something still unresolved). `pendingSince` is deliberately the item's `createdAt`/`submittedAt`, not `updatedAt`, which would keep resetting on every unrelated field edit.

4. **Wired into the existing cron drain**, not a new endpoint: `app/api/internal/jobs/process/route.ts` now also calls `sendDueReminders()` on every hit, unconditionally, the same way `drainWebhookDeliveries`/`drainIntegrationPushes` already do — no new cron schedule needed for reminders to start going out once this ships.
5. No new UI: reminders are a background/email feature, not something with a settings surface of its own the way WP3.1–3.3 needed one (the plan's own wording — "WP3.4 — reminders" — didn't call for one either, unlike the other three).

### A real bug this session's own verification caught (and fixed) before it could ship

The first version of `sendReviewTaskReminders`/`sendExpenseClaimReminders` called `sendReminderEmail` for every recipient with no error handling, then unconditionally stamped `lastReminderAt`. Verifying it against the real Postgres instance immediately surfaced why that's wrong: this local environment has no `RESEND_API_KEY` configured at all (a pre-existing, unrelated gap — see below), so every send throws — and the original code would have let that exception **abort the whole sweep for every other candidate**, and (had the exception come from a partial failure instead) could have stamped `lastReminderAt` on an item nobody was actually notified about, silently giving up on ever reminding anyone about it again. Fixed: each item's send + stamp is now wrapped in its own `try/catch`, logging and moving on to the next candidate on failure, leaving `lastReminderAt` untouched so the next sweep retries it. Verified live: a sweep against a real stale `ReviewTask` failed to send (as expected, no Resend key), logged the failure, left `lastReminderAt` null, and a second sweep retried cleanly with no crash or double-counting.

**Also found via that same verification, filed as a separate background task rather than fixed here**: `resend` (the npm package, already a dependency) declares `@react-email/render` as a required peer dependency for its `react:` send option — which `lib/email.ts` uses for every email this app sends, not just this session's new reminder one. That package is not installed anywhere in `node_modules` or listed in `package.json`. This means **every transactional email this app has ever tried to send via `react:` — invitations, password resets, demo requests, and now reminders — is broken in any environment with a real `RESEND_API_KEY` configured**, confirmed by the exact error Resend's SDK throws (`"Failed to render React component. Make sure to install @react-email/render..."`). This local dev environment never surfaced it before because `RESEND_API_KEY` was empty here, so no email send had ever actually reached that code path until this session's reminder-sweep verification forced one. Not a regression from this session — nothing here added or removed that dependency — but a real, pre-existing production bug this work happened to be the first thing to trip over.

## What's NOT done here

- **No UI to create a plain (manual, workflow-less) ReviewTask.** This is a pre-existing gap, not something WP3.1/3.2 introduced: `createReviewTaskAction` has existed since WP10 with no button anywhere calling it (the review-inbox's empty-state copy even says "...or when someone adds one manually from a document's page", but no such affordance exists on the document page). This session's browser verification had to create test tasks with a one-off `tsx` script rather than through the app, for that reason. Worth fixing at some point independent of Phase 3, since it also blocks a natural "start a workflow on this document" entry point from the document page itself.
- **Nothing automatically starts a workflow, on a ReviewTask or an ExpenseClaim.** The only way either gets a `workflowId` today is a manual picker at review/submit time — no per-supplier-rule "always route through this workflow" option (the way `AutomationRule` today has `requireReview`/`autopublish` booleans), no per-workspace "default workflow" setting. A natural, small follow-up rather than a redesign.
- **No editing an existing draft claim's receipts** — `createExpenseClaim` takes its full document list up front; there's no add/remove-item-from-a-draft affordance (delete-and-recreate is the only path today). `replaceApprovalWorkflowStages` has the identical gap on the workflow side — the model function exists and is tested, only the settings-page affordance for editing an existing workflow's stages is missing (you'd delete and recreate there too).
- **No accounting push for an approved claim.** The `expense-approvals` module's own description says "...and publish employee expense claims" — "publish" meaning push to QuickBooks/Xero the way `accounting-push` already does for invoices/receipts. Not built; an approved `ExpenseClaim` today just sits at `status: "approved"` with no further action.
- **No in-app notification for a reminder, only email** — and email itself is currently broken in any environment with `@react-email/render` missing (see above). There's also no per-workspace or per-user way to opt out of reminders, and no digest/batching (each due item sends its own email immediately when the sweep finds it).
- **WP3.5 (finance-agent approval proposals)** — untouched. The pattern to follow when it's built: a new `describeApprove/RejectWorkflowStage`-style function in `lib/finance/actions.ts` per entity (`ReviewTask` and `ExpenseClaim` each need their own, since they're separate tables) plus a matching Act tool in `app/api/ai-chat/route.ts`'s `financeTools` object — the tool's `execute` must only ever return the proposal, never mutate; the eventual Accept click should call `decideReviewTaskStageAction`/the equivalent expense-claim action, exactly the way today's `approve_review_tasks` tool calls the existing `bulkUpdateReviewTaskStatusAction`.
- **The RLS enable-list gap** (flagged in every recent Dext-parity handoff) is still unaddressed and now also applies to `approval_workflows`/`approval_workflow_stages`/`expense_claims`/`expense_claim_items`: each gets its own inert `CREATE POLICY`, matching the established per-table convention, but none is in the actual `ENABLE ROW LEVEL SECURITY` list (`20260822010000_enable_row_level_security`). `review_tasks` itself has been in this same state since WP10 — Phase 3 does not make it worse, but does not fix it either.
